# 设计取舍：为什么是「进程内库」而不是「网关 + 独立 PDP」

这份文档回答一个具体问题：**为什么不直接用 OPA / 独立 PDP 服务，而要把决策引擎
编译进每个站点？**

它不是「我们做得更好」，而是**明确写下这套方案能做什么、不能做什么**，让读者在
五分钟内判断是否适合自己。

---

## 1. 两种形态

### A. 网关 + 独立 PDP（常见做法）

```
请求 → 网关(PEP) → HTTP → PDP 服务 → 策略库
                       └→ HTTP → PIP（取资源属性）
```

代表实现：OPA + Envoy、Spring Cloud Gateway + 独立鉴权服务。

**特点**
- 策略集中存放，改策略不用重新部署业务
- 决策逻辑与业务代码彻底解耦
- 但每个请求多一跳 RPC，PDP 是单点

### B. 进程内库（本项目）

```
请求 → 站点进程 → import abac.lume → 读本地资源表 + 本地账号表 → 判定
```

**特点**
- 决策零网络往返
- 引擎挂不了（它是代码，不是服务）
- 但策略变更需要改配置/重建镜像

---

## 2. 本项目的决策链

`shared/abac.lume` 的 `decide_with()` 是 **deny-by-default** 的七步短路链：

| # | 检查 | 失败结果 | 可配置 |
|---|---|---|---|
| 1 | 认证是否开启 | 开启则继续，关闭则直接 PERMIT | — |
| 2 | 资源类型是否已知 | DENY | 资源表 |
| 3 | 动作是否在资源允许集内 | DENY | 资源表 `actions` |
| 4 | 账号属性是否可读、账号是否已登记 | DENY（fail-closed） | 账号表 |
| 5 | 角色等级是否达到资源最低要求 | DENY | 资源表 `min_role` |
| 6 | 学段是否在授权白名单内 | DENY | 账号表 `stages` + 资源表 `stage_resource` |
| 7 | 环境属性是否满足规则 | DENY | 资源表 `env.deny_when` |

任一步 DENY 即短路返回，**并写一条审计**。

### 第 7 步：环境属性

第 7 步让「属性」不只限于主体。规则写在资源表里：

```json
"admin": {
  "actions": ["manage"],
  "min_role": "admin",
  "env": {
    "deny_when": [
      { "fact": "hour", "not_in": [9, 18],
        "reason": "no-admin-actions-outside-business-hours" }
    ]
  }
}
```

支持的事实：`hour`（0-23）、`weekday`（0-6，0=周日）。
支持的条件：`not_in`（落在 `[a,b)` 之外）、`eq`、`ne`。

命中后 reason 会写明是哪个事实、违反哪条规则：

```
[env.hour=22 violates 'no-admin-actions-outside-business-hours']
```

**为什么放在 JSON 而不是代码里**：规则变了只改配置、不用重建镜像——这是「策略
可配置」的最小实现，同时保住零网络决策。

**为什么排在第 6 步之后**：先确认主体与资源合法，再看环境。否则「资源不存在」
这类信息可能通过环境拒绝的 reason 泄露出去。

## 3. 能力边界（诚实版）

### 能做的

| 能力 | 说明 |
|---|---|
| 主体属性 | `role`、`stages`、`grade`、`title` |
| 资源属性 | 资源类型、允许动作、最低角色（资源表声明） |
| 环境属性 | `hour`、`weekday`（可扩展） |
| 两层身份模型 | 中央定 `role`，本地定 `stages`，适合多站点共用一套身份 |
| fail-closed | 账号表读不到 → 全部 DENY，绝不降级放行 |
| 审计 | 每个 DENY 留痕，含完整决策链 trace |
| 零网络决策 | 整个判定在站点进程内完成 |

### 做不到的

| 限制 | 影响 | 替代方案 |
|---|---|---|
| **无策略表达式引擎** | 不能写 `subject.clearance < resource.requiredClearance` 这类跨属性比较 | 需要任意表达式时用 OPA / SpEL |
| **无 REVIEW 三态** | 只有 PERMIT / DENY，不能转人工审批 | 金融、风控场景需要独立 PDP |
| **无行级过滤** | 只能判「能否访问**这个**资源」，不能过滤列表 | 需要列表级过滤时在业务层二次调用 |
| **无策略优先级** | 七步顺序固定，不能按优先级合并多条策略 | 规则冲突多的场景需要 deny-override 机制 |
| **规则变更需改配置** | 改 JSON 即时生效，但改链路逻辑要动代码 | 高变更频率场景用数据库存策略 |
| **无策略命中记录** | 审计记录的是决策链 trace，不是「命中了哪条策略」 | 合规审计要求策略级留痕时需要独立 PDP |

## 4. 什么时候该选哪个

| 你的情况 | 建议 |
|---|---|
| 规则以「角色 + 分组」为主，一年改几次 | **本项目**（简单、快、无单点） |
| 每页几十次判定，延迟敏感 | **本项目**（零网络） |
| 希望引擎挂掉不影响业务 | **本项目**（引擎是库） |
| 业务方要自己配规则、频繁调整 | 网关 + PDP |
| 需要跨属性数值比较、复杂布尔表达式 | 网关 + PDP（OPA / SpEL） |
| 需要「大额转人工审批」这类三态 | 网关 + PDP |
| 需要列表级数据过滤 | 网关 + PDP + 业务层 PIP |
| 合规要求「决策命中哪条策略」 | 网关 + PDP |

## 5. 已知的实现细节（踩过的坑）

**`htpasswd` 文件作为认证源**

站点通过 `server { htpasswd = env("HTPASSWD_FILE") }` 把认证交给 HTTP 运行时，
运行时读文件、按 mtime 热重载。这样做的好处是改密码不用重启，代价是：

- 依赖文件系统 mtime 语义（某些网络卷上可能不触发热重载）
- 没有版本号，多站点各自缓存时存在短暂的中间态

对比 JWT 方案（属性随请求携带，天然一致），代价是 JWT 过期前改不了权限。

**lume 的 `/` 恒为 float**

`(t / 3600) % 24` 会抛 `'%' does not apply to floats`，即使整除。
必须先 `int(整个除法结果)` 再取模：`int(t / 3600) % 24`。

**审计目录必须预先存在**

`audit_write()` 的 `mkdir` 失败会被 `try()` 吞掉（注释当作「已存在」），随后
`write_file` 也失败——审计静默丢失，不报错。容器镜像里必须显式创建 `state/`。

## 6. 与 `spring-abac` 的对照

同一作者在 `work/spring/spring-abac` 里实现了形态 A：9 个 Spring Boot 服务 +
网关 PEP + 独立 PDP（`abac-service`），策略存 H2、用 SpEL 求值、支持 REVIEW 三态
和行级过滤。

两者是**同一问题的两种取舍**，不是新旧替代关系：

| | kb-abac（本项目） | spring-abac |
|---|---|---|
| 决策位置 | 站点进程内 | 独立 PDP 服务 |
| 决策耗时 | 0 次网络 | ≥1 次 RPC |
| 策略存储 | 资源表 JSON | 数据库 |
| 表达式能力 | 固定原语 | SpEL，任意表达式 |
| 效果 | PERMIT / DENY | PERMIT / DENY / REVIEW |
| 单点 | 无 | PDP 挂了全站不可用 |
| 变更成本 | 改 JSON 即时生效；改链路需发版 | 改数据库，无需发版 |

选型时先问三个问题：**规则会频繁变吗？需要任意表达式吗？能接受一个决策单点吗？**
三个都答「是」→ spring-abac；三个都答「否」→ 本项目。
